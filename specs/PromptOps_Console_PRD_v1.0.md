# OpenCode 调度追踪系统需求文档

**文档版本：V1.0**  
**文档类型：产品需求文档**  
**系统暂定名称：PromptOps Console**

本需求文档只描述系统的使用场景、产品能力、业务规则和功能边界，不规定技术架构、数据库结构或具体实现方式。同时修正 Task 示例，确保任务模板完整包含执行端点、Prompt、工作目录、模型和定时调度配置。

---

## 1. 产品概述

### 1.1 产品定位

PromptOps Console 是一个面向 OpenCode 的任务调度与执行追踪系统。

用户可以将需要重复执行的工作定义为任务，配置执行内容、OpenCode 端点、工作目录、模型和调度规则。系统按照配置向指定的 OpenCode Serve 发送 Prompt，并记录每次执行过程和最终结果。

系统的核心能力包括：

1. 管理多个 OpenCode Serve 端点。
2. 创建和管理 Prompt 任务。
3. 按计划自动触发任务。
4. 手动立即运行任务。
5. 查看每次任务执行的状态和日志。
6. 查看 OpenCode 在执行过程中调用的 Skill、Tool 和产生的结果。
7. 查询和回溯历史执行记录。

### 1.2 核心业务关系

```text
OpenCode Endpoint
        │
        └── Task
              │
              ├── Schedule
              │
              └── Run
                    │
                    └── Execution Trace
```

各对象含义如下：

- **Endpoint**：一个可接收任务的 OpenCode Serve 端点。
- **Task**：定义要向 OpenCode 发送什么 Prompt，以及何时、在哪里、使用什么模型执行。
- **Schedule**：定义任务自动触发的时间和周期。
- **Run**：任务的一次具体执行。
- **Execution Trace**：一次 Run 中实际发生的消息、Skill 调用、Tool 调用、错误和最终回复。

## 2. 项目背景

当前已经基于 OpenCode 构建了多个工作流 Skill，用于完成不同类型的工作，例如：

- 定期生成报表。
- 整理知识库。
- 汇总业务数据。
- 分析项目文件。
- 检查代码。
- 生成文档。
- 执行固定的业务处理流程。

这些能力可以通过向 OpenCode 发送 Prompt 触发。OpenCode 收到 Prompt 后，根据工作目录中的配置和任务内容，自主判断是否需要调用 Skill、Tool 或其他能力。

目前主要存在以下问题。

### 2.1 工作依赖人工触发

用户需要手动进入 OpenCode，并重复发送相同或相似的 Prompt。

例如：

```text
处理本月的工时数据，并生成 Rate Report。
```

对于每日、每周或每月重复执行的工作，人工触发效率较低，也容易发生遗漏。

### 2.2 缺少统一的任务配置

不同任务可能使用不同的：

- OpenCode Serve 端点。
- Prompt。
- 工作目录。
- Provider 和模型。
- 执行时间。
- 重复周期。
- 超时时间。

目前缺少统一位置管理这些配置。

### 2.3 缺少执行历史

任务发送后，用户缺少统一的历史记录用于回答以下问题：

- 任务什么时候执行了？
- 任务发送到了哪个 OpenCode 端点？
- 使用了哪个工作目录和模型？
- Prompt 是否发送成功？
- OpenCode 是否完成了本次执行？
- 最终返回了什么结果？
- 任务为什么失败？

### 2.4 缺少执行轨迹

OpenCode 在处理 Prompt 时可能调用多个 Skill 和 Tool。

例如：

```text
接收 Prompt
  → 加载业务 Skill
  → 读取输入文件
  → 分析数据
  → 修改文件
  → 生成输出文件
  → 返回最终结果
```

用户需要通过一个统一界面查看这些实际发生的操作，而不是只看到任务开始和任务结束。

### 2.5 需要支持多个 OpenCode 端点

用户可能同时运行多个 OpenCode Serve，例如：

- 本地电脑上的 OpenCode。
- 办公服务器上的 OpenCode。
- 专门处理某个项目的 OpenCode。
- 远程服务器上的 OpenCode。

不同任务需要发送到不同端点，因此系统必须支持端点管理，并允许在任务中选择目标端点。

## 3. 产品目标

### 3.1 任务自动化

用户可以将一个 Prompt 配置为周期性任务，由系统按照指定时间自动发送给 OpenCode。

### 3.2 多端点管理

用户可以配置多个 OpenCode Serve 端点，并为不同任务选择不同端点。

系统应提供一个默认端点，新建任务时自动选择该端点。

### 3.3 执行透明化

用户能够查看每次执行过程中实际发生的操作，包括：

- Prompt 提交。
- OpenCode 回复。
- Skill 调用。
- Tool 调用。
- 文件相关操作。
- 错误信息。
- 最终结果。

### 3.4 历史可追溯

每次任务执行都应形成独立历史记录。即使之后修改了任务配置，历史执行仍然保留当时实际使用的配置和结果。

### 3.5 失败可定位

当任务因端点不可访问、认证失败、模型错误、Tool 调用失败或其他原因无法完成时，用户可以通过执行状态和日志定位问题。

系统暂时不主动监控端点健康状态。端点问题只在连接测试或任务实际执行时体现。

## 4. 目标用户和使用场景

### 4.1 工作流开发者

已开发多个 OpenCode Skill，希望将这些能力配置为自动执行的任务。

典型使用场景：

1. 创建一个每日知识库整理任务。
2. 设置任务每天晚上执行。
3. 选择包含知识库 Skill 的工作目录。
4. 系统按时向 OpenCode 发送 Prompt。
5. 用户第二天查看执行结果和轨迹。

### 4.2 业务用户

不关心具体调用过程，只希望某项工作能够定期完成，并在失败时及时发现问题。

典型使用场景：

1. 配置一个月度报表任务。
2. 设置为每月第一个工作日上午执行。
3. 执行后查看最终回复。
4. 如果失败，查看错误日志和失败位置。
5. 修复输入数据后手动重新执行。

### 4.3 系统管理员

负责管理 OpenCode Serve 端点和默认配置。

典型使用场景：

1. 添加本地 OpenCode 端点。
2. 添加远程 OpenCode 端点。
3. 测试端点是否可以正常连接。
4. 将本地端点设置为默认端点。
5. 控制端点是否允许继续接收新任务。

### 4.4 问题排查人员

需要了解某次任务执行期间具体发生了什么。

典型使用场景：

1. 找到失败的 Run。
2. 查看发送的 Prompt 和实际任务配置。
3. 查看 Skill、Tool 和消息轨迹。
4. 定位出错的 Tool 调用。
5. 查看错误输入、错误信息和最终回复。
6. 根据原配置重新执行任务。

## 5. 核心概念

### 5.1 Endpoint

Endpoint 表示一个 OpenCode Serve 端点。

Endpoint 保存以下信息：

- 端点名称。
- 端点描述。
- 服务地址。
- 认证方式。
- 是否为默认端点。
- 是否允许被新任务选择。

Endpoint 仅表示连接目标，不负责定义任务内容和调度时间。

### 5.2 Task

Task 是一个可重复执行的任务模板。

Task 定义以下内容：

- 要向 OpenCode 发送的 Prompt。
- Prompt 发送到哪个 Endpoint。
- OpenCode 使用的工作目录。
- 使用的 Provider 和模型。
- 是否指定 Agent。
- 任务何时自动执行。
- 任务是否启用。
- 上一次执行未结束时如何处理下一次触发。
- 单次执行允许持续多长时间。

Task 不定义 OpenCode 内部必须执行哪些步骤，也不要求 OpenCode 必须调用某个 Skill。

### 5.3 Schedule

Schedule 是 Task 的组成部分，用于定义任务的自动执行规则。

Schedule 可表达以下类型：

- 周期性执行。
- 指定时间执行一次。
- 固定间隔执行。
- 不自动执行，只允许手动运行。

Schedule 必须包含时区，避免部署位置变化后出现执行时间偏移。

### 5.4 Run

Run 表示 Task 的一次具体执行。

Run 可能由以下方式产生：

- 定时触发。
- 用户手动执行。
- 用户重新执行历史 Run。

每个 Run 都应保存当次执行实际使用的配置，包括：

- Endpoint。
- Prompt。
- 工作目录。
- Provider。
- 模型。
- Agent。
- 调度触发时间。
- 执行策略。

Task 后续发生修改时，不改变已经产生的 Run。

### 5.5 Execution Trace

Execution Trace 表示 OpenCode 对本次 Prompt 的实际处理轨迹。

轨迹可能包含：

- 用户 Prompt。
- Assistant 消息。
- Skill 调用。
- Tool 调用。
- Tool 输入和输出。
- Tool 错误。
- 文件变化。
- 子任务或子会话。
- 最终回复。

系统展示实际获取到的轨迹，不根据 Prompt 推测 OpenCode 应该执行什么。

## 6. 典型业务流程

### 6.1 首次使用

```text
进入系统
  → 配置本地 OpenCode Endpoint
  → 测试连接
  → 设置为默认 Endpoint
  → 创建第一个 Task
  → 配置 Prompt 和执行目录
  → 配置模型和定时计划
  → 保存并启用 Task
```

如果系统首次启动时已经提供本地 Endpoint 配置，则系统应直接将其作为默认端点。

### 6.2 定时执行

```text
到达计划时间
  → 系统根据 Task 创建 Run
  → 读取该 Run 的配置快照
  → 连接目标 Endpoint
  → 创建 OpenCode Session
  → 发送 Prompt
  → 记录执行状态
  → 收集执行轨迹
  → 保存最终回复
  → Run 结束
```

### 6.3 手动执行

```text
用户进入 Task
  → 点击“立即执行”
  → 系统创建新的 Run
  → 使用当前 Task 配置执行
  → 用户进入 Run 详情查看进度
```

手动执行不改变 Task 原有的下一次定时执行时间。

### 6.4 历史重新执行

```text
用户进入历史 Run
  → 点击“重新执行”
  → 系统创建新 Run
  → 使用原 Run 的配置重新执行
  → 新 Run 记录其来源
```

历史重新执行不是恢复原 Run，而是创建一次新的独立执行。

### 6.5 端点连接失败

```text
调度触发
  → 系统尝试连接 Task 指定的 Endpoint
  → 连接失败或认证失败
  → Run 标记为失败
  → 保存错误日志
  → 用户在执行历史中查看失败原因
```

系统暂时不提前监控 Endpoint 的健康状态。

## 7. 功能需求

### 7.1 Endpoint 管理

#### 7.1.1 Endpoint 列表

用户可以查看所有已配置的 Endpoint。

每个 Endpoint 至少显示：

- 名称。
- 服务地址。
- 认证方式。
- 是否为默认端点。
- 是否启用。
- 被多少个 Task 使用。

Endpoint 列表不展示实时在线或离线状态。

#### 7.1.2 创建 Endpoint

用户可以创建新的 OpenCode Endpoint。

需要配置：

**基础信息**

- Endpoint 名称。
- Endpoint 描述。

**连接信息**

- 服务地址。
- 认证方式。
- 认证信息。

认证方式至少支持：

- 无认证。
- Basic Authentication。

如果未来 OpenCode Serve 支持或部署环境需要其他认证方式，可继续扩展。

#### 7.1.3 测试连接

用户可以主动点击“测试连接”。

测试结果至少应区分：

- 连接成功。
- 地址不可访问。
- 认证失败。
- 目标服务不是受支持的 OpenCode Serve。
- 服务返回异常。

测试连接只表示测试时刻可以连接，不代表系统会持续监控端点。

#### 7.1.4 默认 Endpoint

系统必须存在一个默认 Endpoint。

新建 Task 时：

- 自动选择默认 Endpoint。
- 用户可以改为其他 Endpoint。

用户可以将其他 Endpoint 设置为默认端点。新默认端点只影响之后创建的 Task，不自动修改已有 Task。

#### 7.1.5 编辑 Endpoint

用户可以修改：

- 名称。
- 描述。
- 服务地址。
- 认证方式。
- 认证信息。
- 是否启用。

Endpoint 修改只影响之后发起的执行，不修改历史 Run 保存的端点信息。

如果 Endpoint 的地址或认证信息发生变化，使用该 Endpoint 的 Task 仍保持引用该 Endpoint，但后续执行使用更新后的连接配置。

#### 7.1.6 停用 Endpoint

Endpoint 停用后：

- 已有关联 Task 仍然保留。
- 不能使用该 Endpoint 创建新的 Task。
- 使用该 Endpoint 的定时 Task 不应继续发送 Prompt。
- 因 Endpoint 被停用而不能执行的定时触发应形成可查询记录，并明确说明未执行原因。

#### 7.1.7 删除 Endpoint

只有满足以下条件时才允许删除：

- 不是默认 Endpoint。
- 没有 Task 正在引用。
- 没有正在执行的 Run 依赖该 Endpoint。

历史 Run 中保存的 Endpoint 信息不能因为 Endpoint 被删除而丢失。

### 7.2 Task 管理

#### 7.2.1 Task 列表

Task 列表至少显示：

- Task 名称。
- Endpoint。
- 工作目录。
- 模型。
- 调度摘要。
- Task 状态。
- 下一次计划执行时间。
- 最近一次 Run 的状态和时间。

支持按照以下条件筛选：

- Task 状态。
- Endpoint。
- 调度类型。
- 最近执行状态。
- 标签。

#### 7.2.2 创建 Task

创建 Task 时需要配置以下内容。

**基础信息**

- Task 名称。
- Task 描述。
- 标签。

**执行目标**

- Endpoint。
- 工作目录。
- Provider。
- 模型。
- Agent，可选。

**Prompt**

- 要发送给 OpenCode 的完整 Prompt。
- 支持多行内容。
- 保存时不得自动添加用户不可见的任务内容。

**定时调度**

- 是否启用自动调度。
- 调度类型。
- 调度规则。
- 时区。
- 下一次执行时间预览。

**执行策略**

- 上一次执行未结束时的处理方式。
- 单次执行超时时间。

#### 7.2.3 Task 完整示例

以下示例用于说明一个完整 Task 应包含哪些业务配置，不限定系统的存储格式。

```yaml
name: Monthly Rate Report
description: 每月根据工时数据生成 Rate Report
status: enabled

endpoint: Local OpenCode

execution:
  working_directory: /workspace/rates-report
  provider: configured-provider
  model: configured-model
  agent: default

prompt: |
  处理当前月份的工时数据并生成 Rate Report。
  使用工作目录中已经配置的工作流和 Skill 完成任务。
  将结果保存到工作目录规定的输出位置，并在完成后说明处理结果。

schedule:
  enabled: true
  type: cron
  cron: "0 9 1 * *"
  timezone: Asia/Shanghai

execution_policy:
  overlap: queue
  timeout_minutes: 60
```

该示例表示：

- 任务发送到 Local OpenCode。
- OpenCode 在指定工作目录中执行。
- 任务每月 1 日上午 9:00 触发。
- 时间按照 Asia/Shanghai 解释。
- 如果上一次执行未结束，新的执行进入队列。
- 单次执行超过 60 分钟后进入超时处理。
- OpenCode 根据 Prompt 和工作目录自行决定调用哪些 Skill 和 Tool。

#### 7.2.4 调度类型

Task 支持以下调度类型。

**不自动调度**

Task 只允许用户手动执行。

适合：

- 尚在调试的任务。
- 临时任务模板。
- 需要人为检查输入后再运行的任务。

**Cron 周期调度**

适合表达：

- 每天指定时间。
- 每周指定日期。
- 每月指定日期。
- 复杂的周期规则。

例如：

```text
每天上午 8:00
每周一上午 9:00
每月 1 日上午 9:00
```

**一次性调度**

Task 在指定日期和时间执行一次。

执行后调度自动结束，但 Task 本身不被删除。

**固定间隔调度**

按照固定时间间隔执行，例如：

```text
每 30 分钟
每 4 小时
每 2 天
```

#### 7.2.5 调度预览

保存 Task 前，系统应展示未来若干次计划执行时间。

预览需要同时显示：

- 任务时区下的执行时间。
- 用户当前所在时区与任务时区不同时的对应时间。

这样用户可以在保存前发现 Cron 或时区配置错误。

#### 7.2.6 编辑 Task

用户可以修改：

- 名称和描述。
- Endpoint。
- 工作目录。
- Provider、模型和 Agent。
- Prompt。
- 调度规则。
- 执行策略。
- 启用状态。

编辑只影响修改后创建的 Run：

- 已结束的 Run 不受影响。
- 正在执行的 Run 不受影响。
- 已经生成并等待执行的 Run 使用生成时保存的配置。

#### 7.2.7 启用和停用 Task

**启用**

启用后，系统按照 Task 的调度规则产生新的 Run。

**停用**

停用后：

- 不再产生新的定时 Run。
- 已经在运行的 Run 继续执行。
- 已经排队的 Run 默认继续执行。
- 用户仍可查看历史记录。
- 用户可以根据权限手动运行该 Task。

#### 7.2.8 归档 Task

归档用于隐藏不再使用但需要保留历史的 Task。

归档后：

- 不再自动调度。
- 不能直接手动执行。
- 仍可查看历史 Run。
- 可以恢复为普通 Task。

#### 7.2.9 复制 Task

用户可以复制已有 Task。

复制内容包括：

- 基础信息。
- Endpoint。
- 工作目录。
- 模型。
- Prompt。
- 调度配置。
- 执行策略。

复制产生的新 Task 默认不启用自动调度，避免保存后立即产生重复任务。

#### 7.2.10 立即执行

用户可以点击“立即执行”。

系统使用当前 Task 配置创建一个新的 Run。

立即执行：

- 不改变下一次计划执行时间。
- 不修改调度规则。
- 仍然遵守并发和重叠策略。
- 在执行历史中标记为手动触发。

### 7.3 调度管理

#### 7.3.1 自动触发

到达计划时间后，系统为 Task 产生一个独立 Run。

每个计划时间最多产生一个对应 Run，不能由于系统重复检查而创建多个相同执行。

#### 7.3.2 时区

每个 Task 的 Schedule 必须独立设置时区。

时区配置属于 Task 的一部分，不能仅依赖系统运行环境的本地时区。

修改时区后，只影响未来执行。

#### 7.3.3 重叠执行策略

当同一个 Task 的上一次 Run 尚未结束，新触发时间已经到达时，支持以下策略。

**Queue**

为本次触发创建 Run，并等待上一次执行结束后再运行。

**Skip**

不执行本次触发，但保存一条 Skipped 记录，并说明原因是上一次执行尚未结束。

系统不得静默丢弃本次触发。

#### 7.3.4 错过执行时间

如果系统在计划触发时间不可用，恢复后支持以下策略。

**Skip**

跳过已经错过的执行时间，不进行补跑。

**Run once**

无论错过多少次，恢复后只补执行一次。

系统暂时不要求逐次补跑所有错过的执行。

#### 7.3.5 Endpoint 不可用

如果调度触发时目标 Endpoint 无法连接：

- 本次 Run 标记为 Failed。
- 保存连接错误。
- 不自动切换到其他 Endpoint。
- 不自动使用默认 Endpoint 替代。
- 后续调度仍按照 Task 原来的 Endpoint 执行。

### 7.4 Run 管理

#### 7.4.1 Run 来源

每个 Run 必须明确记录触发来源：

- Scheduled：按计划触发。
- Manual：手动立即执行。
- Rerun：从历史 Run 重新执行。
- Recovery：系统恢复后补触发。

#### 7.4.2 Run 状态

Run 至少支持以下用户可见状态：

| 状态 | 含义 |
|---|---|
| Queued | 已创建，等待执行 |
| Preparing | 正在准备执行环境 |
| Submitting | 正在向 OpenCode 提交 Prompt |
| Running | OpenCode 正在处理 |
| Waiting | OpenCode 正在等待权限或其他输入 |
| Completed | OpenCode 已结束本次处理 |
| Failed | 执行发生明确错误 |
| Cancelling | 已请求取消，等待确认 |
| Cancelled | 已确认取消 |
| Timeout | 执行超过设定时间并结束 |
| Skipped | 因重叠策略或其他规则未执行 |
| Unknown | 系统无法确认当前执行状态 |

`Completed` 只表示 OpenCode 的本次执行已经结束，不代表业务结果一定正确。

#### 7.4.3 Run 配置快照

每个 Run 必须保存执行时的完整配置：

- Task 名称。
- Endpoint 名称和地址标识。
- 工作目录。
- Provider。
- 模型。
- Agent。
- Prompt。
- 触发时间。
- 调度规则摘要。
- 超时设置。
- 重叠策略。

历史 Run 不应只引用 Task 当前配置。

#### 7.4.4 Run 日志

Run 日志至少应记录：

- Run 创建。
- 进入队列。
- 开始执行。
- 连接 Endpoint。
- 创建 OpenCode Session。
- 提交 Prompt。
- 开始接收轨迹。
- 发生错误。
- 用户请求取消。
- 执行结束。

端点不可达、认证失败等问题统一显示在 Run 日志中。

#### 7.4.5 取消 Run

用户可以取消 Queued 或正在执行的 Run。

取消结果需要区分：

- 取消请求已发送。
- 已确认执行停止。
- 无法确认是否停止。

系统不能在尚未确认停止时直接显示 Cancelled。

取消操作不能撤销 OpenCode 已经完成的外部操作，例如：

- 已修改的文件。
- 已发送的消息。
- 已写入的数据。
- 已调用的外部服务。

#### 7.4.6 Run 超时

Task 可以配置单次执行超时时间。

达到超时时间后：

- 系统请求停止本次执行。
- Run 进入超时处理状态。
- 已确认停止后显示 Timeout。
- 无法确认是否停止时显示 Unknown，并保留相应说明。

#### 7.4.7 重新执行

用户可以从历史 Run 发起重新执行。

重新执行默认使用原 Run 的配置快照，包括：

- 原 Endpoint。
- 原 Prompt。
- 原工作目录。
- 原模型。

如果原 Endpoint 已被删除或停用，系统应要求用户选择可用 Endpoint 后再执行，并清楚记录此次调整。

重新执行产生新的 Run，不覆盖原 Run。

### 7.5 执行轨迹

#### 7.5.1 轨迹内容

系统应展示从 OpenCode 实际获取到的执行内容，包括：

- 用户 Prompt。
- Assistant 输出。
- Skill 调用。
- Tool 调用。
- 文件操作。
- 错误。
- 最终回复。
- 子 Session，可识别时展示。

#### 7.5.2 Tool 调用

每次 Tool 调用至少展示：

- Tool 名称。
- 当前状态。
- 开始时间。
- 结束时间。
- 执行耗时。
- 输入参数。
- 输出结果。
- 错误信息。

Tool 状态至少区分：

```text
Pending
Running
Completed
Failed
```

#### 7.5.3 Skill 调用

只有在 OpenCode 轨迹明确表示调用了某个 Skill 时，系统才显示 Skill 调用。

展示内容包括：

- Skill 名称。
- 调用时间。
- 调用结果或状态。
- 与调用关联的信息。

系统不得根据 Prompt 中出现的 Skill 名称推测该 Skill 已被调用。

Skill 被成功加载不等同于整个任务成功完成。

#### 7.5.4 文件操作

如果 OpenCode 返回了可识别的文件变化，系统可以展示：

- 新增文件。
- 修改文件。
- 删除文件。
- 文件差异摘要。

系统不根据 Tool 名称自行推断文件一定发生了变化。

#### 7.5.5 轨迹完整性

由于连接中断或 OpenCode 提供的信息有限，系统可能无法获得全部中间事件。

执行详情应明确区分：

- 轨迹正常采集。
- 轨迹中间存在缺口，但最终状态已补充。
- 轨迹不完整。
- 无可用轨迹。

系统不能将模型未公开的内部过程描述为完整思考轨迹。

#### 7.5.6 时间线视图

时间线按照实际发生顺序展示，例如：

```text
09:00:00  Run 创建
09:00:01  连接 Local OpenCode
09:00:02  Session 创建
09:00:03  Prompt 已发送
09:00:05  Skill：rates-report
09:00:06  Tool：读取输入文件
09:00:12  Tool：生成报表
09:00:20  Assistant 返回最终回复
09:00:21  Run 结束
```

#### 7.5.7 调用层级视图

在能够确认父子关系时，系统可以按层级展示：

```text
Run
└── OpenCode Session
    ├── Prompt
    ├── Skill：rates-report
    ├── Tool：读取输入文件
    ├── Tool：生成报表
    └── Final Response
```

无法确认 Tool 属于哪个 Skill 时，Tool 仍显示在 Session 下，不强行归类。

### 7.6 执行详情

执行详情页面至少包含以下区域。

#### 7.6.1 执行摘要

展示：

- Task 名称。
- Run 状态。
- 触发来源。
- Endpoint。
- 工作目录。
- Provider 和模型。
- 开始时间。
- 结束时间。
- 总耗时。

#### 7.6.2 Prompt

展示本次 Run 实际发送的完整 Prompt，而不是 Task 当前保存的 Prompt。

#### 7.6.3 实时轨迹

当 Run 正在执行时，用户可以看到新消息和 Tool 状态持续更新。

用户关闭页面或刷新页面，不应影响后台执行。

#### 7.6.4 最终结果

展示 OpenCode 的最终回复。

若 OpenCode 没有返回最终回复，应明确显示：

```text
本次执行没有可用的最终回复。
```

系统不额外调用模型生成总结，也不自动判断业务结果是否正确。

#### 7.6.5 错误信息

如果 Run 失败，应优先展示：

- 失败阶段。
- 错误类型。
- 错误信息。
- 相关 Tool 或 Session。
- 是否可以重新执行。

#### 7.6.6 消耗信息

如果 OpenCode 返回相关数据，可以展示：

- Token 使用量。
- 成本。
- 缓存使用量。

如果 OpenCode 未返回这些数据，系统不自行估算。

### 7.7 执行历史

#### 7.7.1 历史列表

历史记录至少显示：

- Task。
- Run 状态。
- Endpoint。
- 触发来源。
- 开始时间。
- 结束时间。
- 执行耗时。
- 轨迹完整性。

#### 7.7.2 历史筛选

支持按照以下条件查询：

- Task。
- Endpoint。
- Run 状态。
- 触发来源。
- 时间范围。
- 模型。

#### 7.7.3 历史操作

用户可以：

- 查看执行详情。
- 查看轨迹。
- 查看配置快照。
- 重新执行。
- 对正在执行的 Run 请求取消。

### 7.8 Dashboard

Dashboard 用于快速了解系统中的任务和执行情况。

#### 7.8.1 Endpoint 概览

展示：

- Endpoint 总数。
- 默认 Endpoint。
- 启用和停用的 Endpoint 数量。

不展示基于定时探测的实时健康状态。

#### 7.8.2 Task 概览

展示：

- Task 总数。
- 启用 Task 数量。
- 停用 Task 数量。
- 归档 Task 数量。
- 即将执行的任务。

#### 7.8.3 Run 概览

展示：

- Queued 数量。
- Running 数量。
- Waiting 数量。
- Failed 数量。
- Completed 数量。

#### 7.8.4 最近执行

展示最近若干条 Run：

- Task 名称。
- Endpoint。
- 状态。
- 触发来源。
- 开始时间。
- 进入详情的入口。

#### 7.8.5 最近失败

单独展示最近失败的 Run，便于用户快速发现问题。

端点连接失败也在此处体现，而不是通过 Endpoint 健康监控体现。

## 8. 业务规则

### 8.1 Task 不绑定 Skill

Task 只配置 Prompt 和执行环境。

系统不要求用户在 Task 中选择 Skill。OpenCode 根据 Prompt、工作目录和自身配置决定是否调用 Skill。

### 8.2 Run 与 Task 当前配置隔离

Run 创建后，其执行配置不再跟随 Task 变化。

Task 修改不能影响：

- 正在执行的 Run。
- 已排队的 Run。
- 历史 Run。

### 8.3 默认 Endpoint 规则

- 系统必须指定一个默认 Endpoint。
- 新建 Task 默认选择该 Endpoint。
- 用户可以在 Task 中修改。
- 修改默认 Endpoint 不影响已有 Task。
- 默认 Endpoint 不可直接删除。

### 8.4 Endpoint 失败不自动转移

如果 Task 指定的 Endpoint 失败：

- Run 标记为失败。
- 不自动使用默认 Endpoint。
- 不自动选择其他 Endpoint。
- 不在其他机器上重复执行。

这样可以避免同一个任务在错误环境中执行。

### 8.5 执行结束不等于业务正确

系统能够确认的是：

- Prompt 是否提交。
- OpenCode 是否结束处理。
- 是否发生明确错误。
- 返回了什么最终内容。

系统不负责确认：

- 报表数据是否正确。
- 文件内容是否符合业务要求。
- 外部系统是否真正完成业务动作。
- OpenCode 的结论是否准确。

### 8.6 Tool 成功不等于 Run 完成

一个 Tool 执行成功，只说明该次 Tool 调用成功。

Run 是否结束，应以整个 OpenCode Session 的状态和最终结果为准。

### 8.7 不自动重发状态不明的 Prompt

如果系统不能确认 Prompt 是否已经被 OpenCode 接收：

- Run 标记为状态不明。
- 不自动再次发送相同 Prompt。
- 用户根据日志决定是否重新执行。

此规则用于避免产生重复文件、重复消息或重复外部操作。

## 11. 验收场景

### 场景一：创建定时任务

1. 用户创建 Task。
2. 系统自动选择默认 Endpoint。
3. 用户填写 Prompt、工作目录和模型。
4. 用户设置每天上午 9:00 执行。
5. 用户选择 Asia/Shanghai 时区。
6. 系统展示未来执行时间。
7. 用户保存并启用。
8. Task 列表显示下一次执行时间。

**验收结果**：Task 包含完整执行配置和调度配置。

### 场景二：按时自动执行

1. 到达计划时间。
2. 系统产生 Run。
3. Run 使用 Task 当时的配置。
4. 系统向指定 Endpoint 发送 Prompt。
5. OpenCode 自主调用所需 Skill 和 Tool。
6. 系统记录轨迹和最终回复。
7. Run 显示为 Completed 或 Failed。

**验收结果**：用户无需手动进入 OpenCode 即可完成自动触发和结果查看。

### 场景三：端点连接失败

1. 调度产生 Run。
2. 系统连接 Endpoint 失败。
3. Run 标记为 Failed。
4. Run 日志显示连接错误。
5. 系统不切换到其他 Endpoint。
6. Dashboard 最近失败中可以看到该 Run。

**验收结果**：无需 Endpoint 健康监控，也能从实际任务日志定位端点问题。

### 场景四：查看 Skill 和 Tool 轨迹

1. 用户打开 Run 详情。
2. 页面显示实际 Prompt。
3. 页面显示 OpenCode 调用的 Skill。
4. 页面显示 Tool 输入、输出和状态。
5. Tool 失败时显示错误。
6. 页面显示最终回复。

**验收结果**：用户可以了解 OpenCode 实际完成了哪些工作。

### 场景五：修改 Task 后查看历史

1. Task 原来发送到本地 Endpoint。
2. 已经产生一次 Run。
3. 用户将 Task 修改为远程 Endpoint。
4. 用户查看原 Run。
5. 原 Run 仍显示本地 Endpoint 和原 Prompt。
6. 新 Run 使用远程 Endpoint。

**验收结果**：历史执行不被当前 Task 配置覆盖。

### 场景六：上一轮尚未结束

1. Task 设置为 Queue。
2. 新的触发时间到达。
3. 上一轮仍在运行。
4. 系统创建新的 Queued Run。
5. 上一轮结束后，新 Run 开始执行。

如果 Task 设置为 Skip：

1. 新触发不执行。
2. 系统产生 Skipped 记录。
3. 日志说明上一轮尚未结束。

**验收结果**：重叠执行行为与 Task 配置一致。

### 场景七：重新执行历史任务

1. 用户打开历史 Run。
2. 点击重新执行。
3. 系统展示将要使用的原配置。
4. 系统创建新 Run。
5. 原 Run 保持不变。
6. 新 Run 记录其来源。

**验收结果**：历史重新执行可追溯，不覆盖原记录。

## 12. 成功标准

系统投入使用后，应满足以下标准：

1. 用户可以配置多个 OpenCode Endpoint。
2. 用户可以设置默认 Endpoint。
3. 新建 Task 自动选择默认 Endpoint。
4. 每个 Task 可以选择目标 Endpoint。
5. 每个 Task 都可以配置 Prompt、工作目录、模型和定时调度。
6. 用户能够在保存前看到未来执行时间。
7. 系统能够按计划产生独立 Run。
8. 每个 Run 都保留完整配置快照。
9. 每个 Run 都能关联对应的 OpenCode Session。
10. 用户能够查看执行状态、日志、最终回复和实际轨迹。
11. 用户能够看到真实发生的 Skill 和 Tool 调用。
12. 用户能够从 Run 日志定位 Endpoint 连接和认证问题。
13. Endpoint 不可用时，系统不会自动切换执行环境。
14. Task 修改不会覆盖历史 Run。
15. 系统不会把 OpenCode 执行结束错误地描述为业务结果已经验证正确。

## 13. 最终产品定义

```text
PromptOps Console
=
OpenCode Endpoint Manager
+
Prompt Task Scheduler
+
Run Manager
+
Execution Trace Explorer
```

它不是新的工作流引擎，也不是 OpenCode 的替代品。

它解决的是：

```text
把 Prompt 配置成任务
        +
按计划发送到指定 OpenCode
        +
记录每次运行
        +
查看真实执行轨迹和结果
```
